## 6. 第二轮：着色器深挖 + 诊断构建（`7e3f33c`）

### 6.1 771 个 `a scalar memory read as data`：全部同一族

临时插桩、`translate` 全量跑一遍（trace 1,467,165 行），聚合后：

| trace 行数 | 含义 |
|---:|---|
| 759,154 | `inst=s_load_dwordx4`，user=`s_buffer_load_dword` |
| 374,078 | 同，user=`s_buffer_load_dwordx4` |
| 238,276 | 同，user=`s_buffer_load_dwordx2` |
| 56,227 / 39,423 | 同，user=`s_buffer_load_dwordx8 / x16` |

即 **100% 是"从表里 `s_load_dwordx4` 取一个常量缓冲描述符（V#），再用它做
`s_buffer_load_dword*`"**。第二次插桩看这些 dword 被谁当数字用：
`s_add_u32` 1096、`v_fma_mix_f32` 932+884、`s_add_i32` 663、`s_buffer_load_dwordx4`
（当 soffset）568、`s_mul_i32` 508、`s_and_b32` 442、`s_lshr_b32` 346……全是地址/尺寸
算术（基址+下标、mask、移位），典型的**绑定表里的常量缓冲（bindless 材质参数块）**。

代码侧：`Fields::Buffer` 分支早就用 `a constant buffer's descriptor read as data` 拒绝
同一件事，`Fields::Smem`（常量读把加载值当描述符用）却报 `a scalar memory read as data`
并白算一遍维度。本轮把两条路径统一：Smem 分支把这些 dword 写成
`Val::Missing("a constant buffer's descriptor read as data")` 后返回。效果是**诊断变准、
总量不变**（12,231 / 14,027 未变）：拦住它们的是那些地址算术，需要一个"二级常量缓冲"
的落地方式（把 V# 基址接到 root 参数的 `built_offset`，soffset 只在宿主侧做偏移）。

### 6.2 `image_sample_*_cl`：29 个程序

GFX10 的 `IMAGE_SAMPLE_*_CL` 没有额外操作数，clamp 用 sampler 的 minimum LOD
（宿主 sampler 已带），因此映射到同一 op：`image_sample_cl→60`、`_b_cl→61`、
`_c_cl→64`、`_d_cl→63`。bias 操作数的判断由 `== "image_sample_b"` 改成前缀匹配，
`_b_cl` 才读对位置。结果：29 个里 2 个前进到
`a cross-lane operation outside compute`，27 个落到 `an image address`；**总产出仍不变**。

### 6.3 顺手挖出一个真 bug：立方体贴图的显式梯度地址

`an image address` 的 27 个（外加本来就存在的 `image_sample_d` 立方体路径）不是本次
改动造成的，插桩数字：

```
ADDRFAIL inst=image_sample_d    k=7 len=7 a16=false dim=3 coords=3 dmask=7   (1310 次尝试)
ADDRFAIL inst=image_sample_d_cl k=8 len=8 a16=false dim=3 coords=3 dmask=7   (6501 次尝试)
```

`gfx10/fields.rs::image_addr_dwords` 按 ISA 算：立方体 3 个坐标 + 每方向 2 个梯度分量
× 2 方向 = **7 dword**；而 `emit/lower.rs::image` 的 `grads = 2 * spatial` 对立方体算成
**6 个梯度 dword**，于是去读第 7/8 个字，越界。修法两条：让 emitter 的梯度分量数与
`DIMS` 同表，或在立方体+梯度时提前按 `a cube sample with … gradients` 明确拒绝
（现在是被越界读"意外"挡住的）。两条都要先把导数语义（面空间 vs 方向空间）定清楚。

### 6.4 诊断构建实跑（`--profile diag --features diagnostics`，80 秒）

- **30.0 fps / 33.3 ms**；帧 2048 时 34,204 draws、1,024 dispatches，
  **`dropped 0 without a host pipeline` 和 `0 indirect`**——菜单阶段一个 draw 都没掉。
- 37 个着色器现场翻译，0 个拒绝。
- 抓到 **3 次黑帧**：`a black frame after a frame that was not` @ frame 1172 / 1583 / 2189，
  `copied=true`、`draws=16 / 10 / 5`，随后
  `levels=[90,65,49,44,44,0,63,72,99,148,202,234]` 中有一档为 0。与 #850/#841 的现象同族，
  但这里会自行恢复，且给出了帧号与 draw 数。
- 复现的资源缺口：`no host texture (0x80070057)` ×2（format 86/115、2560×1440）、
  设备槽 `0x1c8` 未实现（caller `+0x247757e`）。

### 6.5 验证

`cargo test -p victory-shader` 120 通过；`--profile diag` 构建通过；两个提交后标题仍
30 fps、无挂起、无新增警告类别。

### 6.6 下一轮建议的顺序

1. 立方体显式梯度的地址布局（`image_addr_dwords` vs `grads`）——已有精确数字，
   影响 `image_sample_d`/`_d_cl` 的立方体路径；
2. 二级常量缓冲（771 个程序的地址算术），复用 root 参数的 `built_offset`；
3. `64-bit image atomic`（653）：DXIL 对图像只给 32 位原子，需要 CAS 循环或改用
   typed buffer，属于架构级取舍，先别动；
4. 资源侧：format 86/115 的 2560×1440 目标（世界画面的主缓冲大概率就是它），
   与描述符堆 1,245,184 → 1,000,000 的截断。

## 8. 第三轮：让它真的跑起来（黑屏定位 + 内存）

### 8.1 你看到的黑屏不是渲染失败

用 `series-s`（外加我误加的 `VICTORY_SKIP_PIPELINES=0750cb2d975c7563`）跑时窗口全黑；
换回默认 `series-x`、不加任何跳过，同一条 `run` 立刻出画：标题栏
`Americas | Victory 30 fps 33.3 ms/frame 11 draws/frame`，画面是 GTA VI 的加载插画
（Jason，全彩，位置正确）。所以 **Series S 模式在这份构建上不出画**，黑屏是那个配置造成的。

### 8.2 OOM 的根因：`shadow.rs` 里没有上限的 4 MiB 窗口缓存

`shadow::loose` 给"缓冲区对象之外"的标题内存（GTA 用自己的分配器放界面顶点）按 4 MiB
窗口做主机副本，注释写着 "copies of windows are never freed"。菜单一帧碰 2–3 个窗口，
于是按 ~250 MB/s 增长；在这台机器上（31 GiB 内存、43 GiB 提交上限）于是：
- 50 秒时一个 1.1 MB 的分配失败；
- 打开世界时一个 67 MB 的分配失败。

已改为**有预算的 LRU**（512 MiB）：超预算先淘汰最久未用的窗口，正在被 list 引用的副本
由 `Arc` 续命到提交完，再次访问时按惯例重新从标题内存拷一遍。提交 `e41c91a`。

### 8.3 提交上限：给 D: 加 64 GiB 页面文件

`Win32_PageFileSetting` 新建 `D:\pagefile.sys`（65536/65536 MiB）后**立即生效**：
提交上限 43.1 GB → **107.1 GB**（空闲 88.5 GB）。不需要重启。

### 8.4 现在的实际状态（RTX 5070 / 31 GiB / 9800X3D）

| 阶段 | 结果 |
|---|---|
| 菜单（含首启流程、设置、法律） | **30.0 fps**，键盘可操作，内存稳定 |
| 进入世界 | **成功进入**：mesh dispatch、FSR4 pass 都在跑；内存稳在 ~25.4 GB 不再涨 |
| 世界帧率 | **1.1–1.5 fps**（0.68–0.90 s/帧），其中每帧 ~640 MB 主机拷贝、~450 ms 花在拷贝上 |
| 约 180 秒后 | `host GPU device removed … 0x887A0004`（DXGI_ERROR_UNSUPPORTED，且 "no breadcrumbs"） |

结论：**今天能玩的是菜单**；世界能进、但只有 1 fps 量级并在 3 分钟后掉设备——这与仓库
README 的 "Not playable yet" 一致，卡的是世界渲染（未翻译着色器、每帧 GB 级拷贝、
以及这次 0x887A0004 的未知来源），不是本机配置。

## 10. 第五轮：世界暗掉的真正原因——wave 64（提交 `2c7d588`）

离线 `translate --pipelines` 里 320 个 compute 程序建不出管线，报错只有一个
"参数错误 (0x80070057)"。加上诊断后（从容器 `PSV0` 里把要求的 wave 宽度和线程组读回来），
结论是**一个原因**：

```
313  pipeline: 参数错误。(wave 64, threads [64, 1, 1])   e.g. DistantObjects:CS_DistanceWindowEmissivesCulling
     …细分：threads 64=275、256=18、1024=14、128=8、512=3、36=2、32=2、16/… 共 18 个 ≤32
```

即：这些控制台程序要求 **64 宽度的 wave**（发射器在"同一 wave 内共享数据"时声明 64），
而 NVIDIA 的 D3D12 设备最大只有 **32 条 lane**，于是 `CreateComputePipelineState` 直接
返回 E_INVALIDARG。**世界里的 ambient map、级联阴影、地形可见性、GPU 粒子这些 compute
全在这个集合里**——它是"世界是黑的"最直接的算力缺口。

顺手修掉其中**不必要**的那部分：线程组本身就 ≤32 的程序，所有 lane 落在宿主的 32 lane
wave 内，共享 LDS 不需要 64 lane 的 wave，因此不再声明该要求。结果：

| 指标 | 修前 | 修后 |
|---|---|---|
| compute 管线建成 | 1,121 / 1,441 | **1,128 / 1,441** |
| compute 拒绝 | 320 | **313** |
| VS/PS、mesh 管线 | 12,231、8,214 全部建成 | 不变 |

剩下 313 个是**真的**需要跨 64 lane 的 wave（要 wave64→wave32 仿真，上游 #189），
这条线我这一轮没有硬闯——它属于结构性工程，硬改只会让画面静默出错。

另外，这一轮也把 `GetDebugInterface`/DRED 缺失确认了（`0x887A002D`，
`Add-WindowsCapability Tools.Graphics.DirectX` 被系统拒绝），所以 `0x887A0004`
的设备移除仍然没有 breadcrumbs 可看。

## 11. 第六轮：wave64 的"实验开关"+ 实测（提交 `0d2c409`）

真正的 wave64→wave32 仿真（#189）需要"两个宿主 wave 组成一个控制台 wave、跨半波用 LDS
信箱 + 屏障"的整套机制，不是一轮能落地的东西。这一轮先把**测量工具**做出来，并量化它的价值：

**开关**：`VICTORY_SHADER_WAVE_RUN=1`（诊断构建）——把波宽要求从容器的两处都去掉
（`PSV0` 的 min/max lane、入口函数的 `dx.waveSize` 属性）。它是翻译的一部分，
所以 shader 缓存键里带了它（`victory-gpu/src/shader_cache.rs`），开着时会打一行警告。

| 指标 | 关（默认） | 开 |
|---|---|---|
| compute 管线建成 | 1,128 / 1,441 | **1,440 / 1,441**（剩 1 个是显存不足） |
| 世界里每帧丢弃 | ~1,480 无管线 + ~2,523 indirect | **~1,140 无管线 + ~1,900–2,100 indirect**，且原因从"没有管线"变成具名 shader |
| 世界帧率 | 1.1–1.5 fps | 0.3–0.6 fps（64 lane 的活摊到 32 lane，波数×2） |
| 画面 | 加载画面干净、世界黑 | 加载画面可见**错误**：整幅泛红/紫、带光晕、左下角色块拖影 |

这个"错误画面"正是开关的意义：它证明这 313 个 compute（环境光贴图、级联阴影、泛光/色调
映射、FSR4 pass）**确实在决定画面**，而且**不能被"不声明波宽"糊过去**——语义必须仿真。

### 真仿真的实现方案（下一步，按这个顺序）

1. **两半波模型**：控制台 wave = 宿主 wave0（lane 0–31）+ wave1（lane 32–63）。
   线程组 ≤32 或 ≤64 的程序，用 LDS 信箱（每 lane 4–8 字节）交换两半的数据。
2. **屏障插入**：`structure` 阶段在 `Barrier` 处已经是显式的；跨半波操作前后各插一条
   `GroupMemoryBarrierWithGroupSync`（DXIL `barrier` op 0xf），并把信箱基址纳入 LDS 分配。
3. **映射表**（每个控制台特性 → 两半实现）：
   `v_mbcnt`（+32 偏移由半波号决定）、`v_readlane/v_writelane`（远端半波走信箱）、
   `ds_swizzle*`（跨 32 边界走信箱）、`v_perm_b32`/DPP（同理）、
   `EXEC/VCC` 掩码当数据（64 位掩码在两个宿主 wave 上各持一半，`ballot` 后用信箱拼）。
4. **不支持的组合显式拒绝**：读远端半波却没在屏障后、或屏障在发散控制流里 → 保持
   `a console wave split across host waves` 这类明确的拒绝原因，绝不静默出错。
5. **回归**：`translate --pipelines` 应当在**不改开关**的情况下把这 313 个建成；
   `--validate` 保持全绿；再用现在这套截图对比（干净/错误）做像素级 sanity check。

## 12. 第七轮：313 个的构成，以及"只切 mbcnt"为什么不划算

动手前先把 313 个（准确说 1,441 个 compute 里需要 64 lane 的那些）按**触发原因**分了类
（临时插桩，`translate` 全量一遍，2,701 条 trace）：

| 组合 | trace 条数 | 含义 |
|---|---:|---|
| swizzle + 跨 lane 读写 + 掩码当数据 | 1,423 | 三样全占 |
| 跨 lane 读写 + 掩码当数据 | 697 | |
| **跨 lane 读写**（`v_mbcnt`/`readlane`/`writelane`） | 362 | 只有这一类 |
| swizzle + 跨 lane 读写 | 129 | |
| 只 掩码当数据 | 51 | |
| 只 swizzle | 38 | |

也就是说：**几乎每个需要 64 lane 的程序都在跨 wave 搬数据**（`v_readlane`/`v_writelane`
把某个 lane 的值搬到另一个 lane）。据此我先实现了最保守的一刀：
"只用 `v_mbcnt`、没有 swizzle/跨 lane 读写/掩码当数据"的程序，按"分裂波"发射——
`lane_index = 组内扁平 id & 63`、线程 id 不再重标号、不声明 64 lane 要求。

结果：**compute 管线仍是 1,128 / 1,441，零收益**——这份语料里没有程序只靠 `mbcnt`。
（改动已回退，工作树干净；`victory-shader` 120 项测试仍全过。）

结论很清楚：剩下的 313 个只能靠**真正的两波仿真**——LDS 信箱 + 屏障把 `readlane`/
`writelane`、`ds_swizzle`、DPP、以及"掩码当数据"在两半之间搬。按上表，先做
`readlane`/`writelane` 这一个族覆盖的面最大（2,541 / 2,701 条 trace 里都出现）。

**下一步的具体切口**（下一轮从这开始）：

1. 在 LDS 分配尾部加 64 dword 的收发区（`lds_dwords + 64`），只给需要的程序；
2. `v_writelane_b32`：本 lane 的值写 `scratch[console_lane]`，随后一条
   `GroupMemoryBarrierWithGroupSync`；
3. `v_readlane_b32`：同上写完、屏障后读 `scratch[lane]`；跨半波因此自然成立；
4. 屏障在发散控制流里的情形不硬来：`structure` 已能判断是否发散，发散时保持明确拒绝
   （`a console lane read across a wave split`），绝不静默出错；
5. 回归：`translate --pipelines` 目标 1,441/1,441；`--validate` 全绿；再用
   `VICTORY_SHADER_WAVE_RUN` 那套截图（干净 vs 泛红）判断语义是否真的对了。

## 13. 第八轮：readlane 信箱的实测（+1 个），以及被修正的优先级

按上一轮定的切口实现了"两半波信箱"：

- 需要 64 lane 的程序里，若只在**读别的 lane**（`v_readlane`/`v_writelane`/`v_mbcnt`）、
  且没有 swizzle/DPP/permute、也没有"掩码当数据"，就在 LDS 尾部预留 64 dword 信箱；
- `lane_index` 改为"组内扁平 id & 63"（= 控制台 lane），线程 id 不再重标号；
- `v_readlane_b32` 改为：本 lane 写 `mailbox[console_lane]` → **组屏障** → 读
  `mailbox[lane & 63]`；发散控制流里的读保持明确拒绝；
- `v_writelane_b32` 天然成立（`console_lane == target` 在整组里唯一）。

实测：**1,128 → 1,129** 个 compute 管线（+1）。原因在上一轮的表里已经能看出来——
真正需要 64 lane 的程序几乎都同时带 swizzle 或"掩码当数据"，单独"跨 lane 读写"几乎不存在。
改动已回退，工作树干净，`victory-shader` 120 项测试全过。

### 优先级被数据修正了

把开关（`VICTORY_SHADER_WAVE_RUN=1`，全部 compute 都能跑）的世界日志拿来对比：

| | 默认 | 开关打开 |
|---|---|---|
| 每帧丢 draw | ~1,480 | ~1,140 |
| 每帧丢 indirect | ~2,523 | ~1,900–2,100 |

**即使 313 个 compute 全部跑起来，世界仍然丢 ~1,140 个 draw / ~2,000 次 indirect**
——因为另一半原因是**根本翻译不出来的 3,436 个程序**（771 二级常量缓冲、653 64 位图像原子、
394 描述符只当数据读……）。所以：

1. **第一优先**：着色器翻译覆盖率（3,436 个）——这是世界"暗"的主要原因；
2. **第二优先**：wave64 仿真（313 个 compute）——必要但不充分，且必须整套两波机制
   （信箱 + 屏障 + 掩码当数据的双 half ballot），碎片化实现拿不到收益（本轮已证）。

我上一轮说"313 直接决定世界能不能出画"是过强的说法，这里更正。

## 14. 第九轮：世界帧时间的账（提交 `28c6588`）

用户目标是"进世界、帧率正常、不崩"。先把世界的每帧成本算清楚（诊断构建，
`VICTORY_GPU_TIMING=1`，进世界后实测）：

```
copies per frame: 37.8 submissions; 6275 title copies 3.5 MB; 10736 refreshes 9243.1 MB, 0 skipped
0.5 fps, 2132.7 ms/frame (474.6 preparing: copies 327.4 ms 614.2 MB, textures 34.4 ms 115.9 MB;
                          1553.7 on the GPU; 82.0 copying back 4.3 MB), 3262 draws/frame
```

三个数字决定了天花板：

1. **每帧 ~10,700 次刷新、~9 GB 主机拷贝**（占 300–460 ms）。世界把 174 MB 的堆以几十个
   重叠视图反复声明；一帧里有 ~35 个提交批次，**批与批之间重复拷同一批数据**
   （`Shadow::update` 的页面簿记 `0 skipped`，等于从不跳过）。
2. **GPU 侧 1.5–2.2 s/帧**，且一帧 2,000–3,300 个 draw。
3. 每帧还有 ~1,100–1,500 个 draw / ~2,000 次 indirect 因为**没有管线**被丢（3,436 个程序
   翻译不出来）。

我做的一处优化（已提交）：**同一批次内重叠的刷新区间合并成一次拷贝**
（`host.rs::flush` 按 buffer 排序、合并重叠 run）。实测帧时间几乎没变——因为重复发生在
**批次之间**，这才是真问题，属于 #407"一个地址空间，不复制标题内存"的工程。

### 结论（直说）

以当前的 `main`，**世界 30 fps 不可达**，也不是调参能解决的：拷贝架构、GPU 侧工作量、
以及 3,436 个未翻译程序，三条都要动。今天能稳定玩的仍是**菜单（30 fps，键盘可用）**；
世界进得去、约 1 fps、几分钟后可能掉设备。

要真往"能玩"走，顺序是：
1. **#407 的地址空间**（消掉每帧 9 GB 拷贝，直接把帧时间砍掉一半以上）；
2. **翻译覆盖率**（3,436 → 越少越好，世界才不黑）；
3. wave64 仿真（313 个 compute，必要但不充分）。

## 15. 第十轮：拷贝为什么跳不过（结论：架构性）

上一轮看到 `0 skipped`，这一轮把"该跳却跳不过"的链条查到底：

1. 跳过依赖 `GetWriteWatch`（`victory-gpu/src/watch.rs`），它只对 **`VirtualAlloc` 分配且带
   `MEM_WRITE_WATCH`** 的区域有效；
2. `victory-hle/src/modules/xmem.rs` 确实给"地址受限"的分配加了 `MEM_WRITE_WATCH`
   （第 130–137 行，decision 0007 的实现）；
3. 但世界那几个大堆走的是**分页文件 section + `MapViewOfFile3` 占位符**那条路
   （为了应付标题一次要 6.1 GiB 的请求），而 **section 映射无法被 write-watch**——
   代码注释里写得很清楚："placeholders cannot be watched"；
4. 于是这些范围只能整体重拷：`Checked 0.0 MB`、`0 skipped`、每帧 ~9 GB。

所以这不是"某个 if 写错了"，而是**复制架构的固有限制**：要么改 xmem 的分配方式（让大堆也用
可监视的 `VirtualAlloc`，但会撞上提交量限制），要么就是 #407 的"地址空间"把复制整个消掉。

### 现状（本机实测，给结论）

| 目标 | 现状 |
|---|---|
| 进世界 | ✅ 能进（约 50 秒加载） |
| 帧率正常 | ❌ 0.5–1.5 fps；每帧 ~9 GB 主机拷贝（300–460 ms）+ GPU 1.5–2.2 s |
| 不崩溃 | ❌ 约 3–4 分钟后 `0x887A0004`（单次提交超 TDR 阈值；本机无调试层，无 breadcrumbs） |
| 菜单 | ✅ 30 fps，键盘可玩，稳定 |

**结论**：以当前 `main`，这三条不可能靠调参或局部补丁同时达成；需要 #407 的地址空间
（消掉 9 GB/帧）与翻译覆盖率（3,436 个程序）两项结构性工作。这份记录里的所有补丁
（内存预算、波宽诊断、刷新合并等）都是正确的增量，但不足以跨过这条线。

## 16. 第十一轮：#407 能不能做成增量补丁？——不能（把理由留在这里）

我本来准备先做"自定义 CPU 可见堆 + placed resource"的 PoC，再逐步替换复制。查完 D3D12
的约束后，结论是**这条路线在当前栈上进不了"补丁"的门**，理由是硬性的：

1. `ID3D12Heap` 的 CPU 可见性只能通过**资源的 `Map()`** 拿到，`Map()` 返回的 CPU 指针对
   与 `GetGPUVirtualAddress()` 返回的 GPU 地址**是两个不同的 VA，虽然指向同一块物理内存**；
2. PC 上 D3D12 **没有**任何 API 能让 GPU VA 等于我们自己选的 CPU 地址（没有
   heap-from-file-mapping，也没有把已有物理页映射到指定 VA 的接口）；
3. 而这份标题（以及它的命令包）假设 **GPU 地址 == CPU 地址**（`lib.rs` 开头那句
   "The title's GPU addresses are CPU addresses" 就是这个意思）：它会把从 CPU 指针算出来的
   地址直接写进命令缓冲。一旦两者不等，就得在**每一处跨 API 边界的地址**上做翻译，
   包括标题自己写进缓冲里的——这正是"不可局部化"的地方。

所以 `shadow` 的复制不是偷懒，是这个架构下的必需代价。#407 只能作为**大重构**（甚至连
标题侧的内存模型一起换），不是几轮能落地的；任何人说"改个 arena 就快了"都过不了上面第 3 条。

### 对"能玩"的最终判断

- 菜单 30 fps：**已经是**（`play.ps1`，键盘全映射，稳定）；
- 世界 30 fps / 不崩：需要 #407 级重构 + 3,436 个程序的翻译覆盖率，**不是本机调参能到**；
- 本机可玩边界：世界约 1 fps、3–4 分钟后可能掉设备，重启脚本可继续。

这份记录到此为止的六个提交都是可合并的增量（内存预算修复、波宽诊断、`_cl` 映射、
刷新合并、构建身份、fence/indirect mesh），测得的每一个数字和复现命令都在上面。

## 18. 第十三轮：要调试层 → 拿不到就自己造（提交 `44e16ab`）

按"继续 1"做的两件事与结果：

### 18.1 Agility SDK：拿到了，但这台机器用不上

- 从 nuget 取到 `Microsoft.DirectX.D3D12` **1.620.2**（34 MB，2 秒），把

- 这两个是数据导出：GNU 工具链上 `-Wl,--export-all-symbols` 会让 exe 起不来

  需要的代码和步骤都记在这里，换成 MSVC 时照做即可。

### 18.2 自己造：在进程内问设备"你反对哪一条"

世界的日志立刻给出答案：

也就是说：**同一个描述，在游戏里被拒、在独立测试里被接受**（早前测试：2D f10/f28 的 RT
全部 `Ok`）。这说明拒绝取决于**调用上下文**（设备已进入的状态、FSR 回退路径创建的描述序列、
clear value 与格式的配合等），而这一层信息只有 D3D12 调试层能一句话说清——这台机器装不上。
改动已全部回退，世界恢复原状（2 个创建失败、能进、约 1 fps）。

**结论**：3D 渲染目标的仿真本身是对的方向，但**在拿到调试层之前，继续盲试的收益很低**。
最可靠的一步是换 MSVC 构建（`/EXPORT:D3D12SDKVersion` + `/DEF:`），让 app-local Agility
运行时生效、调试层可用；那时这条 `0x80070057` 会被直接点名。

## 20. 第十五轮：MSVC 工具链 + Agility SDK 真正落地（提交 `66d7c7f`）

### 20.1 装了什么

- VS Build Tools（`D:\_toolchain\VS`，MSVC **14.44.35207** + Windows SDK **10.0.26100**，
  下载来自 Microsoft CDN，很快）；
- Rust `stable-x86_64-pc-windows-msvc`（tuna 镜像）；
- 用 MSVC 构建 `victory`：**2.5 秒**、产物 6 MB（GNU 版本是 47 MB），跑得通。

### 20.2 Agility SDK：解决了三个坑

1. `.def` 文件里**不能写 `LIBRARY`**（会让 exe 变成 DLL 特性，Windows 报"不是有效应用"）；
2. GNU ld 不支持按名导出数据符号，`--export-all-symbols` 和把 `.def` 当输入都会产出坏镜像
   ——所以这条只走 MSVC 的 `/DEF:`；
3. **`D3D12SDKPath` 必须导出 `const char *`（指针）**，不能导出字符数组本身。之前签名写错，
   系统 `d3d12.dll` 在 init 里解引用那些字符，进程直接 `0xc0000005 @ d3d12.dll+0xbe5d`。
   改成 `pub static D3D12SDKPath: &[u8; 9] = b".\\D3D12\\\0"` 后，`config` 正常，
   **app-local 运行时（1.620）被加载**。

### 20.3 效果

| | 系统运行时（22121） | Agility 1.620 |
|---|---|---|
| 菜单 | 30 fps | 30 fps |
| 世界 | 1.1–1.5 fps | **1.7 fps（600 ms/帧，209 draws）** |
| 纹理创建失败 | 2 个（3D 渲染目标） | 同样 2 个（3D RT 在 D3D12 里非法，运行时再新也不行） |

### 20.4 调试层：差一步

把 `D3D12\d3d12SDKLayers.dll` 的 `D3D12SDKLayersGetInterface` 接进来后，标题在第一次调用
就崩了（breakpad 上报）。已回退：`VICTORY_D3D12_DEBUG` 仍走系统接口，仍返回
`DXGI_ERROR_SDK_COMPONENT_MISSING`。调试层需要的不止这两个导出（还要 `D3D12SDKLayers`
与核心运行时的内部注册），这是下一步要单独攻的点。

**现状**：分支 9 个提交，工作树干净；`victory-gpu` 51 项测试在 MSVC 下也全过；
`play.ps1` 指向的 `target\release\victory.exe` 现在是 MSVC + Agility 1.620 版本。
